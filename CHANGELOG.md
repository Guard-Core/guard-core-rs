# Changelog

All notable changes to this project.

## [Unreleased]

### Added

- The reference pipeline's rate-limit tiers (`guard_core_engine::rate_limit::RateLimiter::check_tiers`, mirrored from `RateLimitCheck.check` in the reference `rate_limit.py` via the Go port's `tiersFor`/`runTier`): the endpoint tier (`endpoint_rate_limits[url_path]`, the new `RateLimitConfig` map field), the route tier (`RouteRateLimits`, the decorator's `rate_limit` with the reference default window of 60), the geo tier (the decorator's `geo_rate_limits` country map, the resolved country's entry with the `"*"` fallback, resolved through a `GeoIpHandler` and never applied without one), and the global tier. Every configured tier records one hit into its own `(ip, path)` window (independent budgets, exactly as the references count) and the first tier that crosses decides, naming its tier and carrying its window for `Retry-After`. The tier entries (`RateLimitEntry::new`, `RouteRateLimits::new`, and the limiter config constructor) fail closed on zero requests or windows (`ge=1`). Without any tier configured the behavior is byte-identical to the previous global-only window
- The tier surfaces on the tower stage (`guard_core_rs::tower`): `RateLimitStage::decide_for_path` resolves the endpoint tier from the request path, the decorator tiers from a `RouteRateLimits` request extension or the builder's `route_resolver` seam (`path -> Option<RouteRateLimits>`, the same route seam the request-limits and user-agent stages use; the extension wins), and the geo tier from the builder's `geo_handler` seam (`Arc<dyn GeoIpHandler>`); a tier crossing answers the same `429` + `Retry-After` shape and feeds the auto-ban engine exactly as the global tier does; `decide` keeps its signature and runs the global tier only

## [4.1.0] - 2026-09-26

### Added

- The request size and content-type pipeline stage (`guard_core_engine::request_limits` + `guard_core_rs::request_limits`), the Rust family's counterpart of the reference engine's `request_size_content` check (`request_size_content.py`): `ContentLimits` carries the route-scoped knobs (`max_request_size`, `allowed_content_types`, both `Option`, the all-`None` default inert), and `RequestLimitsStageLayer`/`RequestLimitsStageService` is an ordinary `tower::Layer` that resolves a path's limits through a `RouteLimitsResolver` (`path -> Option<ContentLimits>`, the tower counterpart of `request.state.route_config`) and answers the reference shapes - size first (`413 "Request too large"` for a `content-length` over the limit, a missing or empty header passing, the parse mirroring Python's `int()` including whitespace, a leading sign, and negative values passing), then the media type (the exact untrimmed prefix before `;`, case-sensitive, `415 "Unsupported content type"`, a missing header blocked by any non-empty allowed list), and the fail-secure `500 "Security check failed"` for a non-integer `content-length` (the reference's `int()` `ValueError` under `fail_secure = True`). Not mirrored: `EVENT_CONTENT_FILTERED` events, `log_activity`, `passive_mode`, the `on_block` hook, and `custom_error_responses` body overrides
- The blocked user-agent pipeline stage (`guard_core_engine::user_agent` + `guard_core_rs::user_agent`), the Rust family's counterpart of the reference engine's `user_agent` check (`user_agent.py`): `UserAgentFilter::new` compiles the `blocked_user_agents` regexes with the reference compiler's case-insensitive + multiline flags and fails closed on ReDoS-unsafe entries (`_validate_blocked_user_agents_value`'s rejection, the same validator) and on uncompilable ones; `is_blocked` truncates the `User-Agent` value to its first 512 code points (`_MAX_USER_AGENT_MATCH_LENGTH`) and matches with search semantics, a missing header reading as the empty string. `UserAgentStageLayer`/`UserAgentStageService` is an ordinary `tower::Layer` that passes for `is_whitelisted || is_exempt` (an `IpGateDecision` request extension), consults a per-route filter resolver before the global list (`check_user_agent_allowed`'s order), answers `403 "User-Agent not allowed"` (with or without a client IP), and feeds the reference's `escalate_identity_violation` shape: only a `ThreatFinding` marked `is_threat` counts (empty categories record `uncategorized`), under reason `Blocked user agent: <truncated agent>`, through a shared `IpBanManager`/`ViolationCounters` pair (`ban_engine` seam) or a private pair. Not mirrored: `log_activity`/event emissions, `passive_mode`, and the `log_sensitive_*` redaction of the agent in reasons
- The required-headers and authentication pipeline stage (`guard_core_engine::headers_auth` + `guard_core_rs::headers_auth`), the Rust family's counterpart of the reference engine's `required_headers` and `authentication` checks (`required_headers.py`, `authentication.py`, `helpers.extract_credential`), evaluated in the reference pipeline's order: required headers first, then authentication. `HeaderAuthRules` mirrors the route fields (`required_headers` in order, `auth_required` scheme, `api_key_required`, `authorization_header_required`, `api_key_header`); the presence scheme short-circuits the other paths; the `bearer`/`basic` schemes demand the exact `Bearer `/`Basic ` prefixes and other schemes carry the whole header value; a header absent or empty answers `400 "Missing required header: {name}"`, a mismatched value `400 "Header '{n}' does not match the required value"` (the dynamic default bodies), and every authentication failure - including a required credential with no verifier - answers the fixed `401 "Authentication required"`. Verifiers resolve route-first with the stage-level global fallback (`SecurityConfig.auth_verifier`); the Rust verifier is a predicate (no principal payload, no verifier-exception path). Not mirrored: `log_activity`, `EVENT_DECORATOR_VIOLATION` events, `passive_mode`, and `custom_error_responses` body overrides
- The cloud-provider blocking pipeline stage (`guard_core_engine::cloud_provider` + `guard_core_rs::cloud_provider`), the Rust family's counterpart of the reference engine's `cloud_provider` check (`cloud_provider.py`, the selector registry, and `_validate_block_cloud_providers_value`): `parse_cloud_selectors` parses the `block_cloud_providers` syntax (bare names and `":!region"` carve-outs) and fails closed on an unknown provider among `VALID_CLOUD_PROVIDERS`; `CloudIpTable` is the in-memory range store the adapter feeds (`set_provider_ranges`, shared across clones so a background refresher can swap ranges under an installed stage); `is_cloud_ip` walks the selected providers with family-strict membership, skipping unloaded providers and honoring carve-outs only for networks whose region is known (providers without region data block whole under a carve-out). `CloudProviderStageLayer`/`CloudProviderStageService` passes for `is_whitelisted \|\| is_exempt` and for requests without a client IP, and answers `403 "Cloud provider IP not allowed"` with the reference `get_cloud_provider_details` pair on the decision. Not mirrored: the range fetching/refreshing (`cloud_handler` fetchers, Redis caching, `cloud_ip_refresh_interval`) and the route-level override (`RouteConfig.block_cloud_providers` + the `clouds` bypass)
- The geo country blocking pipeline stage (`guard_core_engine::geo` + `guard_core_rs::geo`), the Rust family's counterpart of the reference engine's global country rules (the country branch of `check_ip_access`, `_resolve_country_verdict`/`_evaluate_country_access`, `_validate_country_set_value`): `parse_country_lists` uppercases and dedups `whitelist_countries`/`blocked_countries`, `check_countries` applies them in the reference order (a global whitelist match skips - exemption never does, the loopback exemption runs before geolocation, an unresolved address blocks only under a restrictive whitelist with the generic `IP {ip} not in global allowlist/blocklist` reason, the whitelist decides first and outranks the blocklist, membership is exact with no request-time case folding), and `GeoStageLayer` answers the reference `_check_global_ip_restrictions` shape `403 "Forbidden"` with the `IpAccessResult` reason and resolved country on the decision. A request without a client IP mirrors `_check_unknown_identity_access`: blocked only under a restrictive whitelist. The geolocation arrives through the `GeoIpHandler` trait (`get_country(ip) -> Option<String>`, sync and assumed ready); the reference's `MMDB` reading, per-route country rules, verdict logging, and `EVENT_IP_BLOCKED` are not mirrored
- The actix-web and rocket example stages (`examples/actix_app`, `examples/rocket_app`), the second and third pipeline-stage wirings over `guard_core_rs::tower`, reusing `RateLimitStage::decide()` as the single decision point so the family shapes are byte-identical to the tower stage. The actix stage is a `Transform` middleware (`RateLimitStageTransform`/`RateLimitStageService`) that answers the same three shapes (403 banned first, 429 throttled with `Retry-After`, 403 crossing-ban) without hitting the wrapped service, extracts the client IP from `peer_addr()` with the tower default's forwarded-header fallback (leftmost `x-forwarded-for`, then `x-real-ip`, reimplemented over actix's `http` 0.2 types since the facade stage speaks `http` 1.x), and reads the skip state and detection finding from request extensions. The rocket stage is a guard plus ignite fairing plus scoped catchers (the `rocket-guard-rs` adapter's pattern) that stashes the block answer in request-local state, extracts the client IP through Rocket's own `client_ip()` seam (`ip_header`, `X-Real-IP` by default, else the remote peer; documented spoofing caveat for direct exposure), reads the skip state and finding from request-local cache entries, and fails secure with a 500 when the managed stage is absent. Both ship eight tests each in the repo's fake-clock style (throttle crossing and window slide, `Retry-After`, ban answers first, exempt skip with bans still answering, default pass-through, per-identity budgets, IP extraction, auto-ban feed firing on the crossing)
- The rate-limit and dynamic-ban tower stage (`guard_core_rs::tower`), the first pipeline stage over the stateful modules and the Rust family's counterpart of the reference pipeline's `rate_limit` check (`rate_limit.py`), the ban check of `ip_security.py`, and the detection feed of `suspicious_activity.py`: `RateLimitStageLayer`/`RateLimitStageService` is an ordinary `tower::Layer` for Axum/tonic-shaped stacks that checks bans first (403 "IP address banned", no exemption skip, the reference `_check_banned_ip` shape), then rate limits on the global per-IP tier (429 "Too many requests" + `Retry-After: <window>`, skipped for `is_whitelisted || is_exempt` read from an `IpGateDecision` request extension), and feeds the auto-ban engine - a rate-limit crossing counts one `rate_limit` violation (reason `rate_limit_exceeded`) when `enable_rate_limit_auto_ban` is on with the 429 still going out (the ban answers the next request, as in the reference), and a `ThreatFinding` request extension feeds its detection categories (reason `penetration_attempt`, skipped for whitelisted IPs only) with the crossing request answered 403 "IP has been banned". Default IP extraction prefers the peer `SocketAddr` extension, then the leftmost `x-forwarded-for` entry, then `x-real-ip` (custom extractor pluggable). Config is the pair of stateful configs (`RateLimitStageConfig { rate_limit, ip_ban }`, both defaulting off), built fail closed through `RateLimitStage::new`/`builder` (injected clock, trusted proxies, custom extraction); `decide()` is exposed for non-tower adapters to reuse. Not mirrored: the endpoint-rate-limit/decorator/geo tiers, `passive_mode` (no Rust config surface yet), and the suspicious-activity 400 answer below the ban threshold
- `RateLimiter::with_config_and_clock` and `IpBanManager::with_trusted_proxies_and_clock`: the combined construction seams (validated config over an injected clock, trusted proxies over an injected clock) the stage builder and adapter test harnesses need
- Stateful layer: the in-memory sliding-window rate limiter (`guard_core_engine::rate_limit`) and the dynamic IP ban store with the auto-ban engine (`guard_core_engine::ip_ban`), the Rust port of the reference engine's `ratelimit_handler` + `ipban_handler` + threshold helper (via the Go engine's `ratelimit.go` + `ipban.go`), in-memory first with the Redis-distributed mode deliberately out of scope (the store is exactly what both references fall back to when Redis is off)
- `RateLimitConfig` (`enable_rate_limiting` default `false`, `rate_limit` 10, `rate_limit_window` 60 seconds, `enable_rate_limit_auto_ban` default `false`) and `RateLimiter::check`: one sliding log of request timestamps per `(client IP, scope)` - global scope keyed by IP alone, per-endpoint scope keyed by `(ip, path)` - with the reference's in-memory counting (timestamps at or before `now - window` evicted first, `allowed = count < rate_limit`, the block reports `count + 1`, `Retry-After` is the window) and an LRU window store capped at 10 000 keys (`_MAX_TRACKED_RATE_LIMIT_KEYS`); a disabled limiter allows without recording; `RateLimiter::new` fails closed on a zero limit or window
- `IpBanConfig` (`enable_ip_banning` default `false`, `auto_ban_threshold` 10, `auto_ban_duration` 3600 seconds, `threat_ban_config` map of category to `{threshold, duration}`) with fail-closed validation: `IpBanConfig::new` rejects non-positive thresholds/durations and unknown `threat_ban_config` categories (a key must be a pattern-table category or the `rate_limit` pseudo-category, the reference's `ALL_DETECTION_CATEGORIES | {'rate_limit'}`)
- `IpBanManager`: `ban_ip(ip, duration, reason)` with expiry (`BanError::NonPositiveDuration` on zero; re-banning overwrites), `is_banned` honoring expiry on the Go boundary (banned while `now <= expiry`, dropped strictly past it), `unban`, `reset`; durations beyond the local cap (`LOCAL_CACHE_TTL_CAP_SECONDS`, 3600) are clamped to it like the references' local store (`clampToLocalCap`, `TTLCache(ttl=3600)`); an LRU cap of 10 000 entries with the references' silent overflow; the self-DoS guard refuses loopback (`127.0.0.0/8`, `::1/128`) and configured trusted-proxy targets with `Ok(false)` (`IpBanManager::with_trusted_proxies` parses fail closed); all store keys canonicalize IPv4-mapped addresses to their IPv4 form
- The auto-ban engine: `ViolationCounters` (per-IP per-category counts, LRU capped at 10 000 IPs, `_MAX_TRACKED_SUSPICIOUS_IPS`, empty category lists record `uncategorized`) and `resolve_threshold_ban`/`IpBanManager::register_violations` mirroring `_resolve_and_apply_threshold_ban` (`resolveThresholdBan` in the TypeScript port): per-category `threat_ban_config` entries first in listed order (reason `"<reason>:<category>"`), then the flat threshold against the total of all counted categories; violations count even when banning is disabled, so enabling it later starts from observed history
- Both stateful managers accept an injectable wall clock (`with_clock`) so window sliding and ban expiry are testable without sleeping, and `RateLimiter`/`IpBanManager`/`ViolationCounters` are cheaply clonable (the clone shares the store, the references' singleton semantics), so adapters can keep out-of-band handles (admin unban endpoints, stats) alongside the installed layer
- Global IP gate (`guard_core_engine::ip_gate`), the minimal Rust port of the reference engine's global IP stage and the exempt_ips contract (spec rennf93/guard-core#117): `IpGateConfig::new(whitelist, blacklist, exempt_ips)` parses and validates the three lists once at startup and fails closed on an invalid entry (`IpGateError` names the list and the entry), and `IpGateConfig::evaluate` mirrors the reference ordering - with a non-empty `whitelist` an unlisted, non-exempt IP is denied (`IP not in whitelist`), otherwise a `blacklist` hit is denied (`IP is blacklisted`). `exempt_ips` sets the same skip state a whitelist match sets (`IpGateDecision::is_exempt`, alongside `is_whitelisted`) but never adds a deny path, never opens the whitelist gate, and is only set after the deny checks pass; matching semantics are identical for all three lists (exact, CIDR with host bits cleared, IPv4-mapped parity, no cross-family matches). The adapters' deny paths and skip-state plumbing build on this module
- Request body value extraction in the engine (`body_scan`, `multipart_scan`, `json_walk`, `binary_islands`), porting the reference body-scanning split (guard-core 4.0.4, upstream commit 5f399234, via the Go engine's second-reference port): urlencoded form bodies split into field values scanned under `request_body:form_field`, multipart/form-data bodies split into parts scanned under `request_body:multipart_field` (label name scan, `filename="..."` entry with quote stripping and RFC 2231 extended-filename handling, every raw part header entry, then the payload), JSON bodies walked to their leaves with mongo operator keys (`$where`, `$ne`, ...) reported as direct `nosql` hits, embedded JSON in form/multipart field values walked with the `:embedded_json` leaf-context suffix per level, and the whole-body blob fallback for everything else. Adapters feed every extracted value through the normal detect path instead of the lossy whole-body blob, so `\default` in a form field now flows through the raw-view recon scan
- Binary islands reduction for binary-dense multipart file-part payloads: a file-part payload whose binary artifact characters fill at least a fifth of it is reduced to printable runs of at least the new `DetectConfig::binary_min_run_length` (`detection_binary_min_run_length`, reference bounds 4..=1024, default 16) before pattern scanning, so compressed upload bytes stop producing attack-shaped matches whose rate grows with file size while text genuinely embedded in an upload still scans in full. Text uploads, short or mostly-text payloads, text parts without a filename, and whole-body fallback scans keep their full scan, so raw-body signature coverage stays intact
- Hand-rolled line-based multipart scanner mirroring the email feedparser tolerances the reference relies on: raw header names and case in wire order, folded header values with the raw break kept, colonless lines opening the payload (`MissingHeaderBodySeparatorDefect`), the line terminator before a boundary belonging to the delimiter, transport padding ignored on boundary lines, nested multipart containers expanded in place, and a missing closing boundary keeping the part parsed so far
- `detect_verdict` (PyO3) accepts the new `binary_min_run_length` knob with the reference default of 16

### Fixed

- Recon-category rows now also scan the signal-preserving raw view: the configured preprocessor folds LDAP hex escapes (`\de` -> `Þ`) before the pattern tables run, so separator-prefixed probes such as `\default` or `\report.asp` in query or body values never reached a recon row and went undetected. The raw view carries the original value, the #116 leading-separator gate applies to raw-view matches unchanged (bare words stay innocent outside `url_path`/`unknown`, embedded JSON leaves included), and a (pattern, match) deduplication on the raw-view merge keeps a row that matches in both views a single threat
- Structural matchers fold ASCII case like the reference engine: every builtin row compiles under a global `re.IGNORECASE` (`suspatterns_handler.py`), so the sensitive-path, cms-probing, recon, file-upload and proto-pollution matchers now catch uppercase probes (`/SAP`, `/.ENV`, `Thumbs.DB`, `/DOCKERFILE`, `filename="shell.PHP.jpg"`, `object.prototype.x = 1`) exactly as guard-core does; the four `(?-i:...)` deserialization base64 magic rows stay case-sensitive, which was already correct
- Recon whole-value rows with an optional leading path separator no longer read bare query or body values such as `?system=SAP` or `README.md` as probe paths: on `query_param`/`request_body` (embedded JSON leaves included) those hits are rejected unless the value starts with `/` or `\`, while `url_path` and `unknown` are unchanged and separator-leading probes still fire. Gated rows are derived from the table (recon category plus the `\A[/\]?` anchor), matching guard-core #115 (upstream commit 08f79d67)

### Known differences from Python

- **Entropy over bytes, not code points.** Python `Counter(content)` counts code points; Rust uses a 256-byte array. Multi-byte UTF-8 reaches the `entropy > 4.5` threshold more readily in Rust. Acceptable — entropy is one of four obfuscation heuristics, not a hard gate.
- **Suspicious-pattern context windows slice bytes, not code points.** The Python reference expands the context window ±20 code points around a match; Rust expands ±20 bytes rounded to char boundaries. Identical for ASCII content; positions themselves are code-point indices in both.
- **`ast.parse` injection signal not ported.** Python's `_check_ast_parsing_risk` adds 0.2-0.3 to code injection scores. Not worth a Python parser dependency for a weak signal.
- **Async event plumbing not ported.** `agent_handler`, `correlation_id`, `preprocess_batch` are handler-layer concerns, out of scope.
- **`<?php` pattern corrected.** Python's `r"<?php"` makes `<` optional. Rust uses `r"<\?php"` (correct intent). Filed upstream as guard-core#6.
- **`truncate_safely` output order differs.** Python `insert(0, ...)` yields `[gapN…gap1, region…]`. Rust yields `[gap1, region1, gap2, region2…]`. Invisible in practice — detection is substring-based. Filed upstream as guard-core#7.
- **Base64 detector is broad.** `[A-Za-z0-9+/]{4,}={0,2}` fires on any 4+ alphanumeric run. Faithful port of Python.
